# Status

Vine is a work-in-progress Chrome-hosted PE32/i386 Windows userspace runtime, **not** a generally compatible game player.

## Working integration

- A generic UI selects a read-only game directory, browses within it, inspects a selected PE32 executable, and starts the Chrome Worker using the original bytes.
- Source lookups validate path and file metadata without reading whole assets. Bounded reads verify size, modification time and available snapshot version before and after transfer; PE/DLL image identity and executable save-tree identity retain their hashes. Paired Chrome short-flow measurements reduced launch-to-title from about 128 seconds to 54–55 seconds, with normal opening-scene progression and input; this does not measure full-title performance.
- One non-cloneable Rust `Runtime` owns guest memory and Windows state. Rust/Wasm connects PE mapping and imports, a single v86 execution path, guest memory synchronization, x86 API/COM traps and callbacks, reached Win32/DirectSound/DirectInput/GDI/GDI+/D3D9/WinMM behavior, and bounded WebGL2 presentation. Source DLLs with acyclic static imports are loaded from the selected directory/executable directory, mapped and attached before the EXE starts. A Chrome fixture calls through two transitive DLLs and reuses an attached DLL via `LoadLibraryA`; missing DLLs stop explicitly.
- The separate [Vine-v86 fork at `1d19442`](https://github.com/wakka810/vine-v86/commit/1d19442cea7ba0ca6354f1218f06c468a58c77e6) is published and pinned. A clean checkout builds the CPU Wasm and passes PE32 bootstrap and Chrome integration with the matching browser adapter. Vine-local CPU patch stacks, source overlays and the unused npm v86 package have been removed.
- Same-register JIT SBB32 lowering removes algebraically redundant flag expressions while preserving carry reads and raw lazy state. Four matched Chrome short-flow pairs, including reversed ordering, measured start-to-opening-scene at 12.65 versus 12.38 seconds on average, with each pair lower. Overall wall time differed only slightly (69.82 versus 69.58 seconds); these measurements do not establish a general speed or latency benefit. Title timing and MessagePort latency were mixed, and delays of at least 50 ms did not decrease. Strict CPU state/writeback, compiled alias/nonalias carry cases and Chrome integration checks pass.
- The performance baseline uses exact JIT slice budgets, cached JIT at small slice tails, preserved physical mappings during mirror growth, and checked heap lookup. Stopped API returns preserve code/read translations; cleared dirty pages force another write walk. Ordinary synchronous API completions use a scalar Wasm header and consume borrowed memory deltas before ACK. Initial COM presentation without thread creation consumes borrowed pixels synchronously before ACK; other complex, deferred and media receipts retain owned buffers. SIMD instructions reuse a successful task-state check only within a basic block with no intervening imported helper; memory/MMIO and opaque helpers retain checks. JIT x87 single-precision memory operands combine the existing conversion and arithmetic/stack helpers inside the CPU, preserving their exception flags and read/fault order; stopped JIT faults retain the precise previous instruction pointer. Mapping, protection, overflow, growth and full thread-context restore retain TLB flushing. WebGL uploads fill-free BGRX snapshots directly when row pitch is a multiple of four; the shader preserves channel order and opaque alpha. Undefined snapshots with only black fills use a single opaque black texel; other filled, undefined and odd-pitch snapshots retain owned conversion. All snapshots retain complete boundary validation and borrowed bytes are consumed before ACK. CPU writeback compares fixed-size pages with safe word reads and validates every descriptor before copying any authoritative bytes. Forward and reverse Chrome short-flow profiles measured the guest Present path through Rust, browser submission, delta ACK and CPU resume at 5.63 to 2.63 milliseconds on average after direct BGRX uploads. This excludes preceding guest instructions and exact display scanout. Four forward/reverse short-flow runs reduced initial black Present service from 18.81 to 6.38 milliseconds by avoiding an 8 MiB conversion/upload; their overall wall time remained unimproved (69.56 versus 69.81 seconds). Mapping-page traversal uses direct loops while retaining whole-batch validation. Dirty-page and writeback scratch arrays refill before truncation. Eight matched Chrome short flows measured Worker MessagePort mean RTT at 4.69 versus 3.90 ms, with every corresponding pair lower, and delays of at least 50 ms at 15 versus 12 across 1024 acknowledged samples per variant. Overall wall time (69.74 versus 69.99 seconds) showed no established improvement; this small cohort does not establish a general maximum-latency benefit. These RTT observations do not measure guest input, display or audio latency, or peak memory. Rust, LastError, buffer lifetime/bounds, strict CPU state/writeback, fault/self-modification, growth/overflow and Chrome integration checks pass. These short-flow results do not measure full-title performance.
- Direct API handlers retain endpoint identity and scalar ABI argument counts. Pointer-schema contracts, runtime policies, whole-state serialization, checkpoint/evidence tooling, SQLite storage and the title-specific launcher have been removed. Normal Windows failure results are separate from abnormal runtime faults. Private module/memory tests no longer require exporting their implementation types. Pending state remains for CPU, browser and guest-callback handoffs.
- Stop diagnostics preserve the original fault and report the available Rust thread, CPU instruction pointer, module/symbol, LastError, and bounded recent boundary events. Source checks, prepared release/Chrome integration, and an actual PE32 failure through the production Worker verify this behavior.
- Seventeen small Chrome PE32 fixtures exercise execution, input, callbacks, COM, message boxes, concurrent large heap allocations, rendering pixels, guest DirectShow filters receiving decoded MPEG-1 samples and EOF, DirectSound Lock/Unlock and notification waits, source reads, and guest file operations. Thread joins and event waits also resume when every guest thread initially waits for real browser completion. A fixture writes a nonempty save to game-local OPFS, closes it, starts a fresh runtime, and reads identical bytes. Tests also cover bounds, Windows-932 paths, source immutability, and failed writes without partial publication. Chrome checks actual nonzero Web Audio PCM and silence after Stop; these fixtures do not demonstrate full-title playback.
- External testing of the earlier `12a9ba0` CPU baseline with a verified immutable input copy confirmed one complete route, presentation, input, primary audio, and normal in-story save/fresh-runtime/load. The runtime displayed the ending credits and returned to the main menu. A final integrity check confirmed that the original files were unchanged. This full-title scenario has not been repeated with the performance baseline.
- DirectSound owns PCM bytes, buffer locks, playback state, and notification waits in Rust. Chrome renders PCM through Web Audio and an AudioWorklet. Rust publishes deferred COM changes after the browser acknowledges the resource operation; failed operations preserve the authoritative state. One-shot completion uses a live resource identity, and backend failures stop explicitly.
- Initial PE/DLL mappings are indexed by the process allocator. Main executables and source DLLs share checked placement: conflicting preferred bases relocate into available image slots when the PE provides relocations. A conflict without relocations fails before memory changes.
- Keyboard input updates Rust-owned asynchronous key state and routes key messages to the focused window's thread. Queue removal updates that thread's keyboard state; `TranslateMessage` emits reached control/basic ASCII characters. A Chrome fixture verifies actual WndProc down/repeat/up callbacks and character messages. Unsupported printable conversion stops explicitly; IME and general Japanese text entry remain deferred.
- CPU processing yields to Chrome through a launch-local MessageChannel, whose ports close on exit or failure. Guest Sleep timers and elapsed clocks remain real; Rust selects threads at CPU boundaries.
- Reached `MessageBoxA` notifications use bounded Rust-owned Windows-932 text, button/default/cancel semantics and pending owner identity. Chrome shows a modal resource; only an allowed actual button result resumes the caller. Other guest threads and real Sleep completions continue while it is open. Unsupported flags stop explicitly; a general Windows dialog/message-loop implementation remains deferred.
- Large `HeapAlloc` blocks reserve their page-rounded size through the process address allocator and materialize checked pages on demand. Ordinary allocation and free preserve guest bytes without diagnostic fills; zero initialization, reallocation copies, and protected-range validation remain enforced. Paired Chrome short-flow wall time improved from 80.06 to 78.58 seconds (1.84%). `HeapFree` retires large-block memory owners before address reuse. Large `HeapReAlloc` remains explicitly unsupported.

## Still required

- Expand DLL loading only when reached: cyclic imports and loading previously unmaterialized DLLs at runtime still stop explicitly. The current Chrome fixture verifies static DLL imports, `DllMain` process attach, and reuse—not general Windows DLL search or all dynamic loading variants.
- General compatibility and broad long-run stability remain unverified. **Fixture persistence and synthetic instruction progression are not evidence of full-title save/play compatibility.**

Out of scope for now: x64/PE32+, Win64, D3D11/DXGI, XAudio2, networking, a general game library, and multi-process/desktop emulation. Detailed private scenarios and evidence should be maintained externally; this repository retains only small generic diagnostics and tests.
