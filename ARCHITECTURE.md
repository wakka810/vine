# Architecture

Vine runs original PE32/i386 Windows programs in Chrome. The user selects a directory and executable; the selected source directory is read-only. Rust/Wasm implements guest-visible Windows behavior, while the browser Worker supplies resources, input observations, WebGL2 presentation, Web Audio output, browser delays, and storage.

## Authority and boundaries

- Rust owns PE/module state, guest bytes and protections, Windows paths, process/thread/scheduler, handles, COM identity and refcounts, files and cursors, windows/messages, logical graphics, input, and audio. Browser resource identifiers never double as guest handles or pointers.
- `GuestMemory` is authoritative for guest mapping, ownership, protection, and bytes. Strict uses a separate v86 execution mirror. Reflections/deltas and CPU writeback validate their whole batch, current mapping, owner, protection, and generation before acknowledgement; a rejected batch cannot partly publish guest bytes. The CPU cannot execute a pending reflection or unsynchronized delta.
- `Runtime` routes API/COM traps to the Windows handlers in core; Wasm does not select module or COM-class implementations. `Runtime` retains pending API callback calls by Rust frame ID, validates returns, and coordinates window continuation, exception-unwind retirement, and callback cancellation. Core constructs DllMain argument frames from the registered thread stack before publishing lifecycle changes and selects API versus DLL returns from live pending state. Wasm transports CPU resume data, without a second API callback stack or DLL stack cache; TypeScript does not select the Windows callback kind. Traps decode x86 arguments and perform checked guest reads/writes. Windows failure returns and LastError/HRESULT belong in the handlers. Genuine browser, CPU, guest-callback, and deferred completions retain request/identity/lifetime checks; ordinary synchronous updates validate before mutating.
- TypeScript owns DOM, workers, canvas/WebGL2, Web Audio resources, browser delays, permissions, selected directory handles, IndexedDB capability storage, and OPFS bytes. It does not own Windows handles, logical file cursors, COM refcounts, or the guest clock. Audio buffers and Windows playback state live in Rust. Deferred audio COM calls publish after an actual browser resource acknowledgement; pending identity checks protect completion and one-shot end events.
- File System Access reads the selected source without requesting write permission. Rust owns Windows-932 name/path identity and sandboxing; the browser verifies source observations and reads bounded bytes. Writes go only to a game-local OPFS tree. The fixed temporary-directory path uses this game's root, so temporary files obey the same source-collision and durable-write rules. A guest open/write succeeds only after its required durable browser operation completes; failure cannot advance the logical cursor or publish a handle.

The non-cloneable Rust aggregate `Runtime` owns `GuestMemory`. Preparation moves the mapped executable/DLL memory into it once; API/COM dispatch, callbacks, host completions, SEH and CPU synchronization subsequently use that authority. API routing retains endpoint identity and the stdcall argument count; each direct handler validates the pointers and variants it actually consumes. Owners return ordinary Windows failures directly; diagnostic text does not select return values or LastError. Internal errors propagate abnormal state or memory faults. Core internals and their tests remain private; the Wasm bridge transports binary memory batches and small control DTOs. One separately maintained Vine-v86 fork supplies the CPU/JIT; `prepare:engine` fetches the pinned commit into `.work/vine-v86` and builds its Wasm without Vine-local patches or source overlays.

The independent PE32 backend in `crates/vine-recompiler` owns its decoder/lifter, IR, code discovery, generated Wasm, CPU state, checked execution mirror and invalidation. Its compiler also runs as Wasm in Chrome. The factory accepts an explicit experimental `recompiler` option; the normal launch still selects v86. Tagged CPU snapshots separate private engine layouts, and the independent Rust adapter checks Runtime memory updates and retains CPU writes until GuestMemory accepts them. Compatibility switching, full-title execution and 60 FPS remain unverified. The v86 development fork also supports approximate binary64 x87 arithmetic and bounded JIT-local value runs, with raw80 materialization at exits and the same checked execution-mirror boundaries. The published pin remains the strict comparison; `VINE_V86_SOURCE` selects a separate development checkout. See [INDEPENDENT_BACKEND.md](INDEPENDENT_BACKEND.md) for the migration boundary and memory/exit contract.

Fast is the default when available. It links the development v86 CPU and Runtime into one Wasm module with one allocator. `vine-shared-memory` reserves a stable 2 GiB guest-address arena after an 8 MiB CPU page-table area; `GuestMemory` owns each committed page and its permissions. Guest data uses `guest_base + virtual_address`, with Runtime permission checks and the existing cross-page/fault/SMC slow paths. Runtime and CPU alternate under an exclusive Runtime borrow. CPU stores already update authoritative bytes, so Fast has no CPU writeback journal or mirror payload copies. Host changes still carry mapping/invalidation metadata and require acknowledgement; their generation does not count CPU stores. Plain synchronous Win32 completions resume directly inside Rust, while mapping changes, callbacks, COM, scheduler and browser/OPFS work retain normal handoffs. Guest threads use one execution Worker. Fast currently requires guest addresses below 2 GiB. Strict remains available; the execution-mode name is separate from the x87 numerical option.
